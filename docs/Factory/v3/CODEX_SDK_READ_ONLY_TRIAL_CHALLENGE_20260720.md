This review does not install or repair a runtime or SDK, authenticate, inspect

## Challenge Result

### Verdict

`MORE DISCOVERY` before execution Go.

The proposed two-turn trial is bounded and strategically appropriate, but the
current harness has no proven compatible controller runtime, pinned SDK package
and integrity, or approved authentication path. Those are execution
prerequisites and external effects, not Tier 2 implementation details.

The contract may become execution-ready after one file-only prerequisite pack
pins those facts and a repaired challenge confirms the same narrow trial. This
challenge does not authorize that preparation to install or launch anything.

## Critical Findings

1. No compatible SDK controller runtime is currently proved.
   - Observation: Node/npm are absent; `/usr/bin/python3` is 3.9.6; the separate
     framework Python 3.12 has previously hung in this harness.
   - Risk: an execution task could improvise a global runtime install, repair a
     broken interpreter, or switch SDK language/surface.
   - Required repair: a sponsor-approved prerequisite pack must name one exact
     working runtime executable and version. If none exists, runtime
     installation or repair needs its own explicit authority.

2. The SDK dependency and authentication path are unpinned.
   - Risk: “run the SDK trial” could silently authorize network package
     installation, mutable versions, credential use, login, token handling, or
     paid external calls.
   - Required repair: pin package name/version/source/integrity, isolated
     controller path, authentication disposition, and the two external Codex
     service turns. Never record credential values. Any login or credential
     change must safe-hold.

## High Findings

1. Read-only configuration is not proof of enforced isolation.
   - Risk: a configured sandbox may differ from actual target/process/network
     behavior.
   - Repair adopted: record the exact requested configuration and SDK events,
     compare content-addressed target snapshots, and limit claims to observed
     no-change behavior. Do not claim malicious-worker or kernel-level
     isolation.

2. The controller and worker target could be conflated.
   - Risk: dependency files or logs in the target would make before/after
     evidence ambiguous and expose controller artifacts to the worker.
   - Repair adopted: pin separate external controller and target paths; the
     target contains only one fixture.

3. Resume could become a second uncontrolled mission.
   - Risk: a new thread, changed prompt, stale target, or unreviewed event state
     could be treated as continuation.
   - Repair adopted: resume exactly the recorded thread ID once, only after a
     human checkpoint confirms one safe next action. The resume prompt permits
     no tool call.

4. SDK events may not completely expose worker behavior.
   - Risk: an exact response and unchanged target might be overclaimed as proof
     of no hidden activity.
   - Repair adopted: event completeness is an observed trial property, not an
     assumption. Missing tool/approval/error/status fields cannot yield PASS.
     Even complete observed events do not prove absence of hidden vendor-side
     behavior.

5. The trial could drift into adapter implementation.
   - Risk: reusable code, state transitions, automatic verification, or retry
     logic could create worker-control power.
   - Repair adopted: the controller is one-use trial instrumentation only.
     Factory state remains authored separately; no SDK result can activate,
     verify, complete, resume, or close a mission.

6. Cleanup can erase evidence or touch the wrong path.
   - Risk: automatic deletion of controller/target artifacts weakens replay and
     adds destructive authority.
   - Required repair: the prerequisite pack must state exact retention. Default
     is retain both disposable paths and Factory evidence until a separate
     cleanup decision.

## Medium/Low Findings

- The exact prompt bytes, fixture bytes, and hashes are not yet pinned. The
  formation supplies semantic content only; the prerequisite pack must freeze
  final files before execution.
- A single start/resume pass would establish only one local attended
  observation, not reliability across versions, accounts, machines, models,
  workspaces, or failures.
- Existing Codex desktop authentication may or may not transfer to the SDK.
  Documentation is not local auth proof.
- The app-bundled Codex executable is not evidence that either SDK package is
  installed or that invoking it through an SDK will respect the intended
  settings.
- Controller calls necessarily reach the Codex service. “No external effect”
  would be a false boundary; the later Go must authorize exactly those two
  calls while forbidding worker-originated network use.
- SDK response text is not authority, verification, or evidence admission.

## Fallback Triggers

Any future preparation or execution must safe-hold on:

- absent, unhealthy, incompatible, or changed runtime;
- unpinned or mismatched package/version/source/integrity;
- global install, package-manager bootstrap, or additional dependency;
- login, token request, credential/config mutation, or credential output;
- wrong, pre-existing non-empty, symlinked, or escaping controller/target path;
- unavailable or weaker-than-read-only sandbox;
- ambiguous working-directory binding;
- unexpected thread, turn, event, tool, file, command, approval, network, or
  process activity;
- missing or changed thread ID;
- prompt/fixture hash mismatch;
- target snapshot mismatch;
- request to retry, repair, substitute MCP/app-server/CLI/deep link, or expand
  scope.
